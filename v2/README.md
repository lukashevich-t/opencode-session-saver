# session-saver-v2 (session-saver-v2.ts)

Плагин для **opencode 2.x** (проверено на GUI-версии 2.1.4, она запускает
встроенный CLI `opencode-cli serve`), который автоматически сохраняет сессии в
виде обычных JSON-файлов в **нативном формате экспорта V2**. Позволяет переносить
историю диалогов с ИИ между разными ПК (или просто хранить её как плоские
файлы) **без опоры на внутреннюю базу данных opencode**.

Зачем это нужно: сессии opencode лежат в `~/.local/share/opencode/opencode.db`
(в V2 это ещё и event-sourced база, структуру которой нельзя считать
стабильной), и на разных машинах она разная. Файлы, создаваемые этим плагином,
лежат **в самом проекте** (по умолчанию `ai-sessions/` в корне), их можно
коммитить/синхронизировать вместе с кодом. На другом ПК достаточно один раз
импортировать файл — и история продолжается.

> Это переписанная версия плагина для opencode 1.18.x
> (`/media/tim/Ventoy32/work/ai/opencode-session-saver`). Плагины 1.x и 2.x
> несовместимы: V2 читает только `export default { id, setup }` и полностью
> игнорирует V1-экспорт `server()`. Старый плагин на V2 не запускается вообще
> (в логе — `PluginModule.LoadError`), а этот не работает на 1.18.x.

---

## Требования

- **opencode >= 2.x** (проверено на 2.1.4, desktop GUI)
- Node не нужен: плагин выполняется внутри opencode (Bun), зависимостей нет

## Установка

```sh
mkdir -p ~/.config/opencode/plugins
cp session-saver-v2.ts ~/.config/opencode/plugins/session-saver-v2.ts
```

Добавлять плагин в `opencode.json` не нужно — он подхватывается автоматически
из глобального каталога плагинов (`~/.config/opencode/plugins/`) или проектного
(`.opencode/plugins/`).

Перезапустите opencode (в V2 локальные файлы плагинов подхватываются на лету,
но перезапуск надёжнее) и проверьте, что плагин загрузился:

```sh
~/.config/ai.opencode.desktop/cli/2.1.4-x64/opencode-cli plugin list | grep session-saver
```

Если в колонке ID стоит `-`, плагин не загрузился; причина — в логе:

```sh
grep -a 'failed to load plugin' ~/.local/share/opencode/log/opencode.log | tail -3
```

> Плагины 1.x и 2.x лежат в одном каталоге и **не мешают друг другу**: каждый
> загрузчик молча пропускает чужой файл (в логе — WARN `failed to load plugin`),
> а сам продолжает работать. Поэтому `session-saver.ts` (1.18.x) и
> `session-saver-v2.ts` (2.x) могут сосуществовать в
> `~/.config/opencode/plugins/`.

## Как это работает

Плагин подписывается на поток событий сервера (`ctx.event.subscribe()`) и
сохраняет сессию в формате, который понимает импорт V2:

```jsonc
{
  "info": { ...SessionInfo },          // id, parentID?, title, time, location, projectID, cost, tokens
  "messages": [                         // плоский список, не {info, parts} как в 1.x
    { "id": "msg_…", "type": "user", "text": "…" },
    { "id": "msg_…", "type": "assistant", "content": [ { "type": "text", "text": "…" } ] }
  ]
}
```

Состояния сохраняются **по событиям lifecycle**, а не на каждом шаге:

1. **Конец хода** (`session.execution.succeeded` / `.failed` / `.interrupted`,
   а также `session.idle`) — сессия сохраняется **сразу**, как только модель
   закончила ответ. Это основной момент сохранения: закрывать приложение
   не требуется.
2. **Переименование** (`session.renamed`) — заголовок сессии придумывает модель
   уже после ответа, поэтому файл пересохраняется под новым именем
   (старый удаляется).
3. **Создание новой сессии** (`session.created`) — сохраняется предыдущая активная.
4. **Открытие/просмотр другой сессии** (`session.viewed`, `tui.session.select`) —
   первое событие с другим `sessionID` завершает предыдущую сессию и переключает
   слежение на новую. Тот же механизм работает для `session.status`,
   `session.step.ended`, `session.text.ended`, `session.reasoning.ended`,
   `session.tool.called`, `session.compaction.*` и `session.synthetic`.
5. **Закрытие окна проекта** (`location.shutdown`) — сохраняется активная сессия.
6. **Удаление сессии** (`session.deleted`) — удаляется её файл экспорта и запись
   в индексе.
7. **Выгрузка плагина / выход из opencode** — cleanup-функция, возвращаемая из
   `setup`, финально сохраняет активную сессию (с таймаутом и защитой от падений).

Никаких периодических сохранений на каждый токен/шаг нет.

### Переключение и «продолжение» сессии

- Если вы переключили сессию в GUI (или продолжили её), плагин финализирует
  предыдущую активную сессию.
- Сессии-потомки (subagent/subtask, у которых задан `parentID`) **не** считаются
  переключением — активной остаётся родительская.
- Сессии из других проектов, события которых тоже приходят в поток, игнорируются.
- При продолжении сессии старый файл экспорта **перезаписывается** (тот же
  `sessionID`, та же минута → тот же путь). Путь не плодится.

### Удаление

- `session.deleted` → файл экспорта и запись индекса удаляются (можно отключить).
- Если удаляют активную сессию, слежение за ней снимается.

## Конфигурация

Плагин читает JSON-конфиг (обычные ключи, окружение не требуется). Ищутся файлы
(побеждают проектные поверх глобальных):

- глобальный: `~/.config/opencode/session-saver-v2.json`
- проектный: `<корень проекта>/.opencode/session-saver-v2.json`

Структура и значения по умолчанию:

```jsonc
{
  // Корень для сохранений. Абсолютный или относительно корня проекта.
  "root": "ai-sessions",

  // Сессии с количеством сообщений меньшим, чем это значение, не сохраняются.
  "minMessages": 1,

  // Максимальная длина описания (desc) в имени файла.
  "maxDescLen": 80,

  // Транслитерировать кириллицу в имени сессии (а -> a, б -> b, ...).
  // false — оставить как есть.
  "transliterate": true,

  // Удалять файл экспорта и запись индекса при session.deleted.
  "deleteOnSessionDelete": true
}
```

Пример `~/.config/opencode/session-saver-v2.json`:

```jsonc
{
  "root": "ai-sessions",
  "minMessages": 1,
  "deleteOnSessionDelete": true
}
```

### Расположение файлов

По умолчанию:

```
<корень проекта>/ai-sessions/<ГГГГ-ММ-ДД>/<ЧЧ-ММ>_<описание>.json
```

- `<ЧЧ-ММ>` — локальное время сохранения.
- `<описание>` — транслитерированный (кириллица → латиница) slug от заголовка
  сессии, обрезанный до `maxDescLen`; пустой заголовок заменяется
  на `session_<id_сессии>`-подобное id (например `session_08df6c2a`).
- Внутри `ai-sessions/` лежит `.index.json` — индекс `sessionID → путь`,
  **пересобираемый сканированием самих файлов** (по `info.id`), не из базы opencode.

### Имена с коллизиями

Если в ту же минуту сохраняются две разные сессии с одинаковым описанием,
добавляется суффикс `_2`, `_3`, ... . Если сохраняется **та же** сессия повторно в
течение той же минуты, файл перезаписывается, а старый удаляется — без
размножения.

## Перенос между ПК (основной сценарий)

1. Работали на ПК-1 — плагин сохранил файлы в `ai-sessions/` в проекте.
2. Закоммитили (или перенесли) директорию вместе с проектом на ПК-2.
3. На ПК-2 импортируем сессию. Импорт в V2 — это API `experimental.session.import`,
   поэтому через CLI:

   ```sh
   DIR=/путь/к/проекту
   FILE=ai-sessions/2026-10-11/21-32_opredelenie_aktivnoy_videokarty.json

   jq --arg dir "$DIR" '
     . as $root
     | { info:  (.info
             | .id = ("ses_i" + .id[4:])          # id обязан начинаться с "ses"
             | .location.directory = $dir),
         messages: [.messages[] | .id = ("msg_i" + .id[4:])],  # свои id сообщений
         location: { directory: $dir } }
   ' "$FILE" \
     | opencode api post /api/experimental/session/import --data @-
   ```

   - `id` сессии и `id` сообщений **переименовываются** (`ses_i…` / `msg_i…`):
     иначе импорт падает либо с 400 (`Expected a string starting with "ses"`),
     либо с `UNIQUE constraint failed` в БД, если сессия с такими id уже есть.
   - `location.directory` указывает на проект, в который возвращается сессия.
   - Если у сессии есть `info.revert`, там же нужно заменить `revert.messageID`
     (см. пример: поле сбрасывается, т.к. rollback в новой сессии не нужен).
4. Продолжаем работу с полученной сессией (её id теперь `ses_i…`):

   ```sh
   opencode run --session ses_i<остаток-id> "продолжим"
   ```

   Либо просто откройте её в GUI — плагин при ближайшем ответе модели
   (или переключении/выходе) сохранит её заново уже под новым id и новым именем
   файла. Работает и наоборот (ПК-2 → ПК-1).

## Формат и безопасность записи

- Файл содержит **ровно** `{ info, messages }` — ничего лишнего, поэтому
  импортируется как есть (см. выше; `location` и новые `id` добавляются на
  импорте). Проверено на opencode 2.1.4: round-trip `run → файл → import`
  возвращает сессию со всеми сообщениями.
- Старые файлы, созданные версией плагина для 1.18.x (формат
  `{ info, messages: [{ info, parts }] }`), V2 не импортирует. Когда такая сессия
  пересохраняется плагином (после ответа, при переключении или выходе), она
  переписывается в формате V2.
- Запись **атомарная**: пишется во временный файл, затем `rename` — файл никогда
  не остаётся полузаписанным при падении.
- Удаление старого файла при пересохранении: только после успешной записи нового.
- Повторный экспорт без изменений (та же сигнатура) — **пропускается**, лишних
  файлов не плодится.

### Сигнатура (для пропуска неизменённых сессий)

Считается как строка из: `title`, времени обновления сессии, числа сообщений и
`id`+времен сообщений. Считается одинаково и для живых данных, и для прочитанного
файла — поэтому при продолжении без изменений файл не пересоздаётся, а при любом
реальном изменении — заменяется новым именем.

## Режимы работы

| Режим | Поведение |
|---|---|
| Новая сессия в GUI | сохраняется при первом действии + при выходе |
| `opencode run "..."` | сохраняется по окончании ответа + при выходе |
| Продолжение сессии | старая перезаписывается, файл не плодится |
| Переключение сессии в GUI | предыдущая активная финализируется |
| `session.deleted` | файл + индекс удаляются |
| Subagent/subtask (`parentID`) | не путается с переключением |
| Сессия из другого проекта | игнорируется |

## Ограничения

- Сессии с `messages.length < minMessages` (по умолчанию 1) не сохраняются —
  пустые сессии не плодятся.
- **Компактирование обрезает контекст.** В V2 контекст плагина нет списка сообщений
  и нет экспорта сессии; единственный доступный источник транскрипта —
  `ctx.session.context()`, который возвращает сообщения **после последнего
  компактирования**. Для обычных сессий это полный транскрипт (проверено на
  реальных данных), но если сессия была скомпактирована, то в файле будут только
  пост-компакшн сообщения и само сообщение compaction. Обойти это из плагина в
  V2 нельзя: эндпоинты `/api/session/:id/message` и `/api/experimental/session/:id/export`
  недоступны из контекста плагина (нет ни base URL, ни токена, ни клиента).
  Чтобы архив не терялся, плагин **склеивает** сохранённый ранее файл с текущим
  контекстом: если контекст начинается с сообщения `compaction`, история до
  компактирования сохраняется в файле, а не затирается.
- Чтобы открытая «активная» сессия корректно досохранилась при резком убийстве
  процесса (SIGKILL), плагин полагается на cleanup-функцию из `setup`. Основной
  путь сохранения — конец хода (`session.execution.*`), он не зависит от
  завершения процесса; при жёстком kill может не сохраниться только последний
  кусок диалога.
- Чистое переключение сессии без какого-либо действия (просто «посмотрели» другую
  сессию) может не породить события — в этом случае сохранится активная сессия
  при первом последующем действии или выходе.
- Событие `session.idle` в GUI на практике не приходит (проверено на 2.1.4:
  сервер выставляет `session.time.idle`, но событие в поток не публикует), поэтому
  основной сигнал конца хода — `session.execution.succeeded` / `.failed` /
  `.interrupted`.

## Проверка корректности

Тесты — юнит (чистые функции, in-memory fs) и интеграционные (фейковый `ctx` с
потоком событий, временные каталоги, инъекция часов/homedir; полные сценарии
`session.created` → `session.viewed` → `session.deleted` → cleanup). Запущенный
opencode не нужен:

```sh
node --test session-saver-v2.test.ts
```

Нужен Node ≥ 23.6 (нативный type-stripping для `.ts`; подойдёт обычный node 24).
Тесты запускаются напрямую — без package.json и бандлера. Шов для тестов —
`createSessionSaver({ now, fs, homedir })`, который возвращает `setup`-функцию;
дефолтный экспорт подставляет реальные зависимости (его и грузит opencode).

Проверка типов (строгий `tsc`) и проверка контракта с реальными типами V2 —
см. `AGENTS.md`.
